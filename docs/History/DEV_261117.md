기획: [PLAN_261115_ENGLISH_CHUNKING.md](../Plan/PLAN_261115_ENGLISH_CHUNKING.md)의 "표 → 산문 변환의 수치 손실"(E9, E10). 브랜치 `dev`.

샘플: `test/!251120(보도자료)_주간아파트가격동향(20251117기준).pdf` (15쪽, 표 11개 중 큰 표 6개).

## 원인 측정 (E9)

표 블록 크기별로 LLM 청킹 후 숫자 보존율을 쟀다(기존 코드, 3회).

| 표 크기 | 숫자 보존 | 문서에 없는 숫자 |
| --- | --- | --- |
| 300자 이하 (5개) | 67~100% | 0 |
| 2,000자 이상 (5개) | 2~17% | 블록당 최대 76 |

원인은 두 가지였다.

**1. 파서가 쌓인 칸을 한 행으로 합친다.**
- PDF 표에서 하위 행 경계선이 없으면, PyMuPDF는 여러 행을 한 칸에 줄바꿈으로 담는다.
  - 예: `'수원⏎수원 장안⏎수원 권선'`, `'2.40⏎1.62⏎0.96'`
- `format_table_as_text`가 칸 안의 줄바꿈을 공백으로 바꾼다. 그래서 `| 용인 용인 처인 용인 기흥 용인 수지 | 0.40 -0.59 -0.41 1.57 |`처럼 한 행이 된다.
  - 서울 표는 지역 30개가 한 칸에 들어 있었다.
- 어느 값이 어느 지역 것인지 LLM이 알 수 없다. 앞서 본 "부천과 안산이 같은 값" 오류의 원인이다.
- 이름이 다음 행으로 넘어가는 경우도 있다(값 10줄짜리 '인 천' 행 + 값 없는 '부 산'~'충 남' 행).
  - 이때 기존 빈칸 채우기 규칙이 윗행 값을 복사해서 강원·충북·충남에 충남 값이 들어갔다.

**2. 큰 표를 LLM이 산문으로 풀면서 요약한다.**
- 파서를 고친 뒤에도 숫자 보존이 35~49%에 그쳤다.
- 700자 단위로 나눠 넘겨도 45~51%였다.
- 지역 이름을 빼고 "다른 인천 지역은"으로 쓰거나, 여러 지역을 한 값으로 묶는 오류도 남았다.

## 변경 내용 (E10)

### 쌓인 칸 펼치기 (`parsers._explode_stacked_rows`)

- `format_table_as_text`에서 공백 정규화 전에 실행한다. PDF 표에 공통으로 적용되며, 언어와 청킹 방식(LLM, rule)에 관계없다.
- 펼치는 기준:
  - 줄이 2개 이상인 칸들의 줄 수가 N으로 같으면 N개 행으로 나눈다.
  - 한 줄짜리 칸(상위 지역명 등)은 첫 행에만 두고, 이후 기존 빈칸 채우기가 채운다.
  - 줄이 모자란 칸은 다음 행들에서 이어 받는다. 단, 다음 행에 그 칸 외의 값이 없을 때만 이어 받는다.
    - 예 1: `['부천⏎…'(4줄), 값 28줄]` + `[이름 24줄]`
    - 예 2: `['인 천', 값 10줄]` + `['부 산']` … `['충 남']`
- 펼치지 않는 경우(원래 행 그대로 둠):
  - 줄바꿈 칸이 하나뿐이고 이어 받은 칸도 없는 경우. 머리글의 `10.13⏎(2주 누계)` 같은 경우다.
  - 이어 받아도 줄 수가 맞지 않는 경우

### 큰 표는 원문 표 청크로 (`chunker._split_verbatim_tables`)

- LLM 경로(PDF, DOCX)에서 700자(`TABLE_SPLIT_MAX_CHARS`)가 넘는 표는 LLM에 보내지 않는다.
- `split_large_table_text`로 조각을 나눈다.
  - 각 조각에 머리글 행을 반복한다. 첫 행, 구분선, 그리고 첫 칸이 빈 2단 머리글까지다.
  - 조각은 700자 안팎이다(최대 702자).
- 조각은 그대로 청크가 된다. 첫 줄은 `[표] 매매가격 변동률 (1/3)`이다.
  - 표 제목은 바로 앞 블록이 40자 이하 한 줄일 때만 쓰고, 아니면 번호만 붙인다(`[표] (6/7)`).
- 나머지 블록은 기존처럼 LLM 청킹을 거친다.
  - 결과는 출처 블록 순서로 합친다(`_merge_by_source_order`).
- 700자 이하 표는 기존처럼 LLM이 산문으로 바꾼다.

### 기타

- LLM 청크의 `page`는 출처 블록 중 가장 앞 블록의 페이지로 정한다. 이전에는 LLM이 나열한 첫 블록 기준이었다.
- 표 제목의 PDF 잔여물 `[ ]`를 지운다.

## 실측

보도자료 PDF, LLM 경로(`gemini-2.5-flash`), 각 3회. 비율은 각 조건의 파서 출력에 있는 숫자 기준이다.

| 조건 | 청크 수 | 숫자 보존 (전체 / 큰 표) | 문서에 없는 숫자 |
| --- | --- | --- | --- |
| 변경 전 | 20~23 | 10~15% / 11~15% | 64~88 |
| 파서 수정만 | 21~23 | 35~44% / 38~49% | 208~216 |
| 파서 수정 + 표 700자 분할 후 LLM | 43~46 | 45~48% / 50~53% | 298~343 |
| **파서 수정 + 큰 표 원문 청크 (적용)** | 41~43 | **98~99% / 100%** | **0** |

- "문서에 없는 숫자"의 대부분은 `‘24년` → `2024년` 같은 표기 변경이다. 적용안에서는 0이다.
- 9쪽 시도별 표를 PDF 화면과 대조했다. 21개 행의 값이 모두 일치한다(이전에는 강원·충북·충남에 충남 값).
- 원문 표 청크로 QA를 생성했다(`gemini-3.8-flash`, 9쪽 표 3번째 조각). QA 3개의 수치가 모두 PDF와 일치한다.
  - 예: 경북 누계 -0.83 / -1.66, 제주 11.3~11.17 -0.06 / -0.04 / -0.04
- 영문 논문도 바뀌었다(Attention). 원문 그림과 대조하니 행과 값이 맞게 펼쳐진다.
  - Table 3: 이전에는 여러 행이 한 행으로 뭉쳐 있었다. 지금은 20행이다.
  - Table 4: 12행 모두 그림과 일치한다.
  - Table 3의 하이퍼파라미터 열은 PyMuPDF가 처음부터 한 열로 잡아, 열 구분은 변경 전과 같이 없다.

## 표 안의 표 (중첩 표)

위 작업을 커밋한 뒤(`5969acb`~`f1db4fe`) 중첩 표를 확인했다. 샘플이 없어서 python-docx와 PyMuPDF로 테스트 파일을 만들었다. 구조는 바깥 2×2 표의 한 칸에 3×2 표가 들어 있는 형태다.

| 형식 | 이전 동작 | 문제 |
| --- | --- | --- |
| DOCX | `_cell_text`가 칸 바로 아래 문단만 읽음 | 하위 표 내용이 **통째로 사라짐** |
| PDF | PyMuPDF가 바깥 표와 하위 표를 둘 다 잡음 | 바깥 칸에 하위 표가 한 줄로 뭉쳐 들어가고(`구별 변동률 구 변동률 강남 0.25 송파 0.31`), 하위 표가 한 번 더 나옴 |

DOCX 큰 표에 관한 정정도 있다. 위에서 "DOCX 경로에도 적용했다"고 썼지만 실제로는 동작하지 않았다. DOCX 표 텍스트(`| a | b |` 행을 빈 줄로 구분)에는 `[표]` 머리말과 구분선이 없어서 분할 조건을 통과하지 못했다.

### 변경

- **DOCX** (`_extract_table`):
  - 칸 안의 `w:tbl`을 재귀로 읽는다.
  - 그 칸에는 `구별 변동률 [하위 표]`만 남긴다.
  - 하위 표는 바깥 표 바로 뒤에 `[표] 서울 · 구별 변동률 (하위 표)`를 첫 줄로 하는 별도 블록이 된다.
- **PDF** (`_pdf_nested_tables`):
  - 다른 표 안에 들어 있는 2행·2열 이상의 표를 하위 표로 본다.
  - 바깥 표에서 하위 표가 든 칸은 하위 표 영역 밖의 글자와 `[하위 표]`로 바꾼다.
  - 하위 표의 첫 줄은 DOCX와 같은 형식의 제목이다.
  - 레이아웃 틀은 따로 처리한다. 글자가 있는 바깥 칸이 전부 하위 표를 담고 있으면, 표 두 개를 나란히 놓는 틀로 본다. 이때 바깥 표는 버리고 하위 표는 제목 없이 그대로 둔다.
    - 예: 보도자료 4쪽과 7쪽의 시도별 표 두 개를 감싼 1×2 틀
- **DOCX 큰 표 분할:** `split_large_table_text`는 700자가 넘는 DOCX 표를 `[표]` + 머리글 + 구분선 형식으로 바꾼 뒤 나눈다. 700자 이하 DOCX 표는 이전과 같다.

### 확인

- 테스트 파일:
  - DOCX: 하위 표 내용이 나온다. 바깥 칸에는 `[하위 표]`만 있고, 순서는 바깥 표 → 하위 표다.
  - PDF: 같은 결과이고 중복이 없다.
  - 레이아웃 틀(PDF): 하위 표만 남는다.
- 기존 샘플 3종(보도자료, Attention, BERT): 파서 출력 해시가 이 변경 전과 같다.
  - 처음 구현 때는 보도자료의 레이아웃 틀과 BERT 그림 조각(1행 표)을 하위 표로 잡았다. 그래서 레이아웃 틀 규칙과 2행·2열 하한을 넣었다.
- 단위 테스트 5개를 추가했다. 전체 45개가 모두 통과한다.
  - 중첩: DOCX / PDF / 레이아웃 틀
  - DOCX 표 분할 2개

### 남은 일 (중첩 표)

- 실제 중첩 표가 있는 문서로 확인하지 못했다. 테스트 파일은 단순한 2단 구조다.
- 하위 표 안에 또 표가 있는 3단 중첩은 DOCX만 재귀로 처리한다. PDF는 가장 가까운 바깥 표 기준으로 한 단계씩 처리하지만 테스트하지 않았다.
- PDF 레이아웃 틀 판정은 "글자가 있는 칸이 모두 하위 표를 담음"이다. 틀에 제목 글자가 따로 들어 있으면 중첩 표로 처리된다.

## 남은 일

- **표 앞뒤 문단이 하나로 묶임:** 큰 표를 LLM 입력에서 빼면서, 표 앞 제목·각주와 다음 절 제목이 한 청크로 묶이는 경우가 있다(예: `붙임 1` 제목 + 누계 각주 + `붙임 2` 제목).
- **표 청크의 검색·평가 영향:** 마크다운 표 청크가 임베딩 검색과 RAG 평가 점수에 미치는 영향을 아직 비교하지 않았다.
- **분할 기준 700자:** 보도자료 1종으로 정했다. 표가 많은 다른 문서로 확인이 필요하다.
- **DOCX 표:** 분할·원문 청크는 아래 "표 안의 표" 작업에서 DOCX 표 형식까지 처리하도록 고쳤다. 실제 DOCX 샘플로는 아직 확인하지 않았다.

# xlsx·csv 수집 (2026-11-17)

기획: [PLAN_261117_TABLES_XLSX.md](../Plan/PLAN_261117_TABLES_XLSX.md)의 X1. 결정이 필요했던 값은 기획의 기본값을 그대로 썼다.
- 시트당 2,000행, 문서당 20,000행
- `.csv` 포함, `.xls` 제외
- 숨김 행·열 포함

## 변경 내용

### 파싱 (`ingestion/spreadsheet.py`, 신규)

- `extract_text_by_page`에 `xlsx`, `xlsm`, `csv` 분기를 추가했다.
  - `.xls`는 "엑셀에서 .xlsx로 저장한 뒤 올려 주세요" 메시지와 함께 `ValueError`로 거절한다.
  - 업로드 작업은 텍스트 추출 단계의 `ValueError`만 이 메시지 그대로 실패 사유로 보여 준다. 다른 오류는 이전처럼 일반 메시지다.
- 시트 처리:
  - openpyxl `data_only=True`로 읽는다. 시트 하나가 `page` 하나다.
  - 숨김 시트는 건너뛴다.
- 표 영역:
  - 빈 행과 빈 열로 번갈아 나눠 표 덩어리를 찾는다. 빈 행으로만 나누면 옆에 나란한 표에 왼쪽 표의 빈 행이 붙는다.
  - 값이 2칸 이하인 덩어리는 다음 표의 제목(`[표] 시트 · 제목`)으로 쓴다.
  - 표 없이 남은 메모(각주)는 별도 텍스트 블록이 된다.
- 병합 칸:
  - 병합 범위 전체에 값을 채운다.
  - 덩어리 첫 행에서 시작하는 세로 병합이 있으면 그 아래 행까지 머리글로 본다.
  - 둘째 머리글 행에서는 세로 병합으로 채워진 칸을 비운다. PDF 표와 같은 2단 머리글 형식이 되어, 조각마다 머리글로 반복된다.
- 값 표시는 칸 서식(`number_format`)을 따른다.
  - `0.00%` → `4.31%`, `#,##0` → `12,345`, 날짜 → `2025-11-17`
  - 반올림은 엑셀과 같은 사사오입이다(`55,010.25` → `55,010.3`). 파이썬 기본 반올림은 `55,010.2`였다.
- 수식 칸은 저장된 계산값을 쓴다. 계산값이 없으면 빈칸이 되고, 개수를 경고 로그로 남긴다.
- 행 상한을 넘는 행은 읽지 않는다. 잘린 행 수는 page의 `truncated_rows`와 경고 로그에 남는다.
- CSV:
  - 인코딩은 UTF-8(BOM 포함), CP949 순으로 시도한다.
  - 구분자는 `,`, `;`, 탭 중에서 자동 판별한다.
  - 시트 이름 대신 파일 이름을 쓴다.

### 청킹 (`chunker.ingest_with_table_chunking`, 신규)

- 파이프라인은 스프레드시트일 때 선택한 청킹 방식(`llm`/`rule`)과 관계없이 이 함수를 쓴다.
  - LLM 호출은 없다.
  - metadata의 `chunking_method`는 `table`, 시트 이름은 `sheet`에 들어간다.
- 표마다 `split_large_table_text`로 700자 안팎 조각을 만든다.
  - 조각 첫 줄은 `[표] 시트 · 제목 (k/n)`이고, 머리글 행이 반복된다.
  - 청크 유형은 `table`이다.

### 화면·문서

- 업로드 `accept`에 `.xlsx`, `.xlsm`, `.csv`를 추가했다. 안내 문구는 "PDF, DOCX, XLSX, CSV"다.
- `README.md`의 지원 형식과 표 처리 설명을 갱신했다.

## 테스트

테스트용 엑셀은 openpyxl로 만들었다.

| 시트·파일 | 구성 |
| --- | --- |
| 매매가격 | 시트 제목 칸, 병합 2단 머리글, 퍼센트·쉼표·날짜 서식, 수식 칸, 빈 열 뒤의 옆 표, 각주 |

결과:
- 매매가격 시트: 표 2개 + 각주 1개
  - 2단 머리글이 머리글 행으로 처리된다.
  - 옆 표에 빈 행이 붙지 않는다.
  - 서식 값이 엑셀 화면과 같다.
- 숨김 시트는 제외됐다.
- 일별 로그: 501행이 잘렸다(경고 로그 있음).
  - 청크 110개, 가장 긴 청크 703자
  - 읽은 데이터 1,999행이 하나도 빠지지 않고 청크에 들어갔다.
- 수식 칸: openpyxl로 저장한 파일이라 계산값이 없어 빈칸이 됐다(경고 1건). 의도한 동작이다.
- 언어 판별: `ko`
- QA 생성(`gemini-3.8-flash`, 매매가격 표 청크): QA 2개의 수치가 원본 칸 값과 모두 일치한다.
  - 예: 전국 0.14%/0.61%, 서울 4.31%/7.49%, 부산·제주 주간 값
- 단위 테스트 `backend/tests/test_spreadsheet.py` 7개를 추가했다. 전체 52개가 모두 통과한다.
  - 서식 13가지 사례
  - 시트·영역·병합·제목
  - 계산값 없는 수식
  - 행 상한
  - `.xls` 거절
  - CP949 CSV
  - 큰 시트 청크의 제목과 행 보존
- 회귀 확인:
  - 기존 PDF 3종(보도자료, Attention, BERT)의 파서 출력 해시가 이 변경 전과 같다.
  - 프론트 `tsc --noEmit` 통과
  - 모바일 레이아웃 E2E 13개 통과. 1개는 평가 이력이 없어 건너뛰었다(`test.skip(!hasHistory)`).

## 남은 일

- 실제 업무 xlsx로 확인하지 못했다. 엑셀에서 저장한 파일(수식 계산값 있음)과 복잡한 서식(사용자 정의 서식, 통화, 회계)으로 확인이 필요하다.
- 업로드 완료 화면에 시트 수와 잘린 행 수를 표시하지 않는다(U1).
- 숨김 행·열은 포함한다. 필터로 숨긴 행이 섞인 파일은 결과가 화면과 다를 수 있다.
- 업로드부터 계층 분석, QA, 평가까지 앱에서 끝까지 진행하는 확인은 하지 않았다. 이번 확인은 함수 단위로 했다.
