기획: [PLAN_261115_ENGLISH_CHUNKING.md](../Plan/PLAN_261115_ENGLISH_CHUNKING.md)의 "표 → 산문 변환의 수치 손실"(E9, E10). 브랜치 `dev`.

샘플: `test/!251120(보도자료)_주간아파트가격동향(20251117기준).pdf` (15쪽, 표 11개 중 큰 표 6개).

## 원인 측정 (E9)

표 블록 크기별로 LLM 청킹 후 숫자 보존율을 쟀다(기존 코드, 3회).

| 표 크기 | 숫자 보존 | 문서에 없는 숫자 |
| --- | --- | --- |
| 300자 이하 (5개) | 67~100% | 0 |
| 2,000자 이상 (5개) | 2~17% | 블록당 최대 76 |

원인은 두 가지였다.

**1. 파서가 쌓인 칸을 한 행으로 합친다.**
- PDF 표에서 하위 행 경계선이 없으면, PyMuPDF는 여러 행을 한 칸에 줄바꿈으로 담는다.
  - 예: `'수원⏎수원 장안⏎수원 권선'`, `'2.40⏎1.62⏎0.96'`
- `format_table_as_text`가 칸 안의 줄바꿈을 공백으로 바꾼다. 그래서 `| 용인 용인 처인 용인 기흥 용인 수지 | 0.40 -0.59 -0.41 1.57 |`처럼 한 행이 된다.
  - 서울 표는 지역 30개가 한 칸에 들어 있었다.
- 어느 값이 어느 지역 것인지 LLM이 알 수 없다. 앞서 본 "부천과 안산이 같은 값" 오류의 원인이다.
- 이름이 다음 행으로 넘어가는 경우도 있다(값 10줄짜리 '인 천' 행 + 값 없는 '부 산'~'충 남' 행).
  - 이때 기존 빈칸 채우기 규칙이 윗행 값을 복사해서 강원·충북·충남에 충남 값이 들어갔다.

**2. 큰 표를 LLM이 산문으로 풀면서 요약한다.**
- 파서를 고친 뒤에도 숫자 보존이 35~49%에 그쳤다.
- 700자 단위로 나눠 넘겨도 45~51%였다.
- 지역 이름을 빼고 "다른 인천 지역은"으로 쓰거나, 여러 지역을 한 값으로 묶는 오류도 남았다.

## 변경 내용 (E10)

### 쌓인 칸 펼치기 (`parsers._explode_stacked_rows`)

- `format_table_as_text`에서 공백 정규화 전에 실행한다. PDF 표에 공통으로 적용되며, 언어와 청킹 방식(LLM, rule)에 관계없다.
- 펼치는 기준:
  - 줄이 2개 이상인 칸들의 줄 수가 N으로 같으면 N개 행으로 나눈다.
  - 한 줄짜리 칸(상위 지역명 등)은 첫 행에만 두고, 이후 기존 빈칸 채우기가 채운다.
  - 줄이 모자란 칸은 다음 행들에서 이어 받는다. 단, 다음 행에 그 칸 외의 값이 없을 때만 이어 받는다.
    - 예 1: `['부천⏎…'(4줄), 값 28줄]` + `[이름 24줄]`
    - 예 2: `['인 천', 값 10줄]` + `['부 산']` … `['충 남']`
- 펼치지 않는 경우(원래 행 그대로 둠):
  - 줄바꿈 칸이 하나뿐이고 이어 받은 칸도 없는 경우. 머리글의 `10.13⏎(2주 누계)` 같은 경우다.
  - 이어 받아도 줄 수가 맞지 않는 경우

### 큰 표는 원문 표 청크로 (`chunker._split_verbatim_tables`)

- LLM 경로(PDF, DOCX)에서 700자(`TABLE_SPLIT_MAX_CHARS`)가 넘는 표는 LLM에 보내지 않는다.
- `split_large_table_text`로 조각을 나눈다.
  - 각 조각에 머리글 행을 반복한다. 첫 행, 구분선, 그리고 첫 칸이 빈 2단 머리글까지다.
  - 조각은 700자 안팎이다(최대 702자).
- 조각은 그대로 청크가 된다. 첫 줄은 `[표] 매매가격 변동률 (1/3)`이다.
  - 표 제목은 바로 앞 블록이 40자 이하 한 줄일 때만 쓰고, 아니면 번호만 붙인다(`[표] (6/7)`).
- 나머지 블록은 기존처럼 LLM 청킹을 거친다.
  - 결과는 출처 블록 순서로 합친다(`_merge_by_source_order`).
- 700자 이하 표는 기존처럼 LLM이 산문으로 바꾼다.

### 기타

- LLM 청크의 `page`는 출처 블록 중 가장 앞 블록의 페이지로 정한다. 이전에는 LLM이 나열한 첫 블록 기준이었다.
- 표 제목의 PDF 잔여물 `[ ]`를 지운다.

## 실측

보도자료 PDF, LLM 경로(`gemini-2.5-flash`), 각 3회. 비율은 각 조건의 파서 출력에 있는 숫자 기준이다.

| 조건 | 청크 수 | 숫자 보존 (전체 / 큰 표) | 문서에 없는 숫자 |
| --- | --- | --- | --- |
| 변경 전 | 20~23 | 10~15% / 11~15% | 64~88 |
| 파서 수정만 | 21~23 | 35~44% / 38~49% | 208~216 |
| 파서 수정 + 표 700자 분할 후 LLM | 43~46 | 45~48% / 50~53% | 298~343 |
| **파서 수정 + 큰 표 원문 청크 (적용)** | 41~43 | **98~99% / 100%** | **0** |

- "문서에 없는 숫자"의 대부분은 `‘24년` → `2024년` 같은 표기 변경이다. 적용안에서는 0이다.
- 9쪽 시도별 표를 PDF 화면과 대조했다. 21개 행의 값이 모두 일치한다(이전에는 강원·충북·충남에 충남 값).
- 원문 표 청크로 QA를 생성했다(`gemini-3.8-flash`, 9쪽 표 3번째 조각). QA 3개의 수치가 모두 PDF와 일치한다.
  - 예: 경북 누계 -0.83 / -1.66, 제주 11.3~11.17 -0.06 / -0.04 / -0.04
- 영문 논문도 바뀌었다(Attention). 원문 그림과 대조하니 행과 값이 맞게 펼쳐진다.
  - Table 3: 이전에는 여러 행이 한 행으로 뭉쳐 있었다. 지금은 20행이다.
  - Table 4: 12행 모두 그림과 일치한다.
  - Table 3의 하이퍼파라미터 열은 PyMuPDF가 처음부터 한 열로 잡아, 열 구분은 변경 전과 같이 없다.

## 표 안의 표 (중첩 표)

위 작업을 커밋한 뒤(`5969acb`~`f1db4fe`) 중첩 표를 확인했다. 샘플이 없어서 python-docx와 PyMuPDF로 테스트 파일을 만들었다. 구조는 바깥 2×2 표의 한 칸에 3×2 표가 들어 있는 형태다.

| 형식 | 이전 동작 | 문제 |
| --- | --- | --- |
| DOCX | `_cell_text`가 칸 바로 아래 문단만 읽음 | 하위 표 내용이 **통째로 사라짐** |
| PDF | PyMuPDF가 바깥 표와 하위 표를 둘 다 잡음 | 바깥 칸에 하위 표가 한 줄로 뭉쳐 들어가고(`구별 변동률 구 변동률 강남 0.25 송파 0.31`), 하위 표가 한 번 더 나옴 |

DOCX 큰 표에 관한 정정도 있다. 위에서 "DOCX 경로에도 적용했다"고 썼지만 실제로는 동작하지 않았다. DOCX 표 텍스트(`| a | b |` 행을 빈 줄로 구분)에는 `[표]` 머리말과 구분선이 없어서 분할 조건을 통과하지 못했다.

### 변경

- **DOCX** (`_extract_table`):
  - 칸 안의 `w:tbl`을 재귀로 읽는다.
  - 그 칸에는 `구별 변동률 [하위 표]`만 남긴다.
  - 하위 표는 바깥 표 바로 뒤에 `[표] 서울 · 구별 변동률 (하위 표)`를 첫 줄로 하는 별도 블록이 된다.
- **PDF** (`_pdf_nested_tables`):
  - 다른 표 안에 들어 있는 2행·2열 이상의 표를 하위 표로 본다.
  - 바깥 표에서 하위 표가 든 칸은 하위 표 영역 밖의 글자와 `[하위 표]`로 바꾼다.
  - 하위 표의 첫 줄은 DOCX와 같은 형식의 제목이다.
  - 레이아웃 틀은 따로 처리한다. 글자가 있는 바깥 칸이 전부 하위 표를 담고 있으면, 표 두 개를 나란히 놓는 틀로 본다. 이때 바깥 표는 버리고 하위 표는 제목 없이 그대로 둔다.
    - 예: 보도자료 4쪽과 7쪽의 시도별 표 두 개를 감싼 1×2 틀
- **DOCX 큰 표 분할:** `split_large_table_text`는 700자가 넘는 DOCX 표를 `[표]` + 머리글 + 구분선 형식으로 바꾼 뒤 나눈다. 700자 이하 DOCX 표는 이전과 같다.

### 확인

- 테스트 파일:
  - DOCX: 하위 표 내용이 나온다. 바깥 칸에는 `[하위 표]`만 있고, 순서는 바깥 표 → 하위 표다.
  - PDF: 같은 결과이고 중복이 없다.
  - 레이아웃 틀(PDF): 하위 표만 남는다.
- 기존 샘플 3종(보도자료, Attention, BERT): 파서 출력 해시가 이 변경 전과 같다.
  - 처음 구현 때는 보도자료의 레이아웃 틀과 BERT 그림 조각(1행 표)을 하위 표로 잡았다. 그래서 레이아웃 틀 규칙과 2행·2열 하한을 넣었다.
- 단위 테스트 5개를 추가했다. 전체 45개가 모두 통과한다.
  - 중첩: DOCX / PDF / 레이아웃 틀
  - DOCX 표 분할 2개

### 남은 일 (중첩 표)

- 실제 중첩 표가 있는 문서로 확인하지 못했다. 테스트 파일은 단순한 2단 구조다.
- 하위 표 안에 또 표가 있는 3단 중첩은 DOCX만 재귀로 처리한다. PDF는 가장 가까운 바깥 표 기준으로 한 단계씩 처리하지만 테스트하지 않았다.
- PDF 레이아웃 틀 판정은 "글자가 있는 칸이 모두 하위 표를 담음"이다. 틀에 제목 글자가 따로 들어 있으면 중첩 표로 처리된다.

## 남은 일

- **표 앞뒤 문단이 하나로 묶임:** 큰 표를 LLM 입력에서 빼면서, 표 앞 제목·각주와 다음 절 제목이 한 청크로 묶이는 경우가 있다(예: `붙임 1` 제목 + 누계 각주 + `붙임 2` 제목).
- **표 청크의 검색·평가 영향:** 마크다운 표 청크가 임베딩 검색과 RAG 평가 점수에 미치는 영향을 아직 비교하지 않았다.
- **분할 기준 700자:** 보도자료 1종으로 정했다. 표가 많은 다른 문서로 확인이 필요하다.
- **DOCX 표:** 분할·원문 청크는 아래 "표 안의 표" 작업에서 DOCX 표 형식까지 처리하도록 고쳤다. 실제 DOCX 샘플로는 아직 확인하지 않았다.

# xlsx·csv 수집 (2026-11-17)

기획: [PLAN_261117_TABLES_XLSX.md](../Plan/PLAN_261117_TABLES_XLSX.md)의 X1. 결정이 필요했던 값은 기획의 기본값을 그대로 썼다.
- 시트당 2,000행, 문서당 20,000행
- `.csv` 포함, `.xls` 제외
- 숨김 행·열 포함

## 변경 내용

### 파싱 (`ingestion/spreadsheet.py`, 신규)

- `extract_text_by_page`에 `xlsx`, `xlsm`, `csv` 분기를 추가했다.
  - `.xls`는 "엑셀에서 .xlsx로 저장한 뒤 올려 주세요" 메시지와 함께 `ValueError`로 거절한다.
  - 업로드 작업은 텍스트 추출 단계의 `ValueError`만 이 메시지 그대로 실패 사유로 보여 준다. 다른 오류는 이전처럼 일반 메시지다.
- 시트 처리:
  - openpyxl `data_only=True`로 읽는다. 시트 하나가 `page` 하나다.
  - 숨김 시트는 건너뛴다.
- 표 영역:
  - 빈 행과 빈 열로 번갈아 나눠 표 덩어리를 찾는다. 빈 행으로만 나누면 옆에 나란한 표에 왼쪽 표의 빈 행이 붙는다.
  - 값이 2칸 이하인 덩어리는 다음 표의 제목(`[표] 시트 · 제목`)으로 쓴다.
  - 표 없이 남은 메모(각주)는 별도 텍스트 블록이 된다.
- 병합 칸:
  - 병합 범위 전체에 값을 채운다.
  - 덩어리 첫 행에서 시작하는 세로 병합이 있으면 그 아래 행까지 머리글로 본다.
  - 둘째 머리글 행에서는 세로 병합으로 채워진 칸을 비운다. PDF 표와 같은 2단 머리글 형식이 되어, 조각마다 머리글로 반복된다.
- 값 표시는 칸 서식(`number_format`)을 따른다.
  - `0.00%` → `4.31%`, `#,##0` → `12,345`, 날짜 → `2025-11-17`
  - 반올림은 엑셀과 같은 사사오입이다(`55,010.25` → `55,010.3`). 파이썬 기본 반올림은 `55,010.2`였다.
- 수식 칸은 저장된 계산값을 쓴다. 계산값이 없으면 빈칸이 되고, 개수를 경고 로그로 남긴다.
- 행 상한을 넘는 행은 읽지 않는다. 잘린 행 수는 page의 `truncated_rows`와 경고 로그에 남는다.
- CSV:
  - 인코딩은 UTF-8(BOM 포함), CP949 순으로 시도한다.
  - 구분자는 `,`, `;`, 탭 중에서 자동 판별한다.
  - 시트 이름 대신 파일 이름을 쓴다.

### 청킹 (`chunker.ingest_with_table_chunking`, 신규)

- 파이프라인은 스프레드시트일 때 선택한 청킹 방식(`llm`/`rule`)과 관계없이 이 함수를 쓴다.
  - LLM 호출은 없다.
  - metadata의 `chunking_method`는 `table`, 시트 이름은 `sheet`에 들어간다.
- 표마다 `split_large_table_text`로 700자 안팎 조각을 만든다.

# 평가 v2 (1~4단계)

> 기획: [PLAN_261117_EVAL_V2.md](../Plan/PLAN_261117_EVAL_V2.md). 자체 검토와 GPT 검토 2건(파이프라인 재설계, 다국어 평가)을 합쳤다.
> 기본 평가 경로는 계속 v1이다. v2는 아직 API에 연결하지 않았다.

## 확인한 v1 문제

- **통계 항이 상수다:** `pipeline.py`가 `integrated_score`를 읽는데 `DatasetStats.analyze_all()`은 이 키를 반환하지 않는다. 그래서 통계 항은 항상 5/10, 즉 0.025점이다. v1 이력과 점수를 맞추기 위해 고치지 않고 주석으로 남겼다.
- **실패가 중간 점수로 섞인다:** Judge가 실패하면 0.65(완전성은 0.5)로 대체하는데, 실패 표시가 남지 않는 경로가 있었다. 완전성 Judge가 빈 응답(`{}`)을 주면 기본값 5점이 조용히 들어갔다.

## 변경

| 파일 | 내용 |
| --- | --- |
| `evaluators/rag_triad.py`, `qa_quality.py`, `pipeline.py` | v1: 대체값이 쓰인 QA에 `error`를 남기고, 요약에 `evaluation_error_count`를 추가했다. 점수는 바뀌지 않는다. `error`가 있으면 기존 `evaluation_error` 실패 유형으로 분류된다. |
| `evaluators/data_validation.py` (신규) | Stage 1. 구문 탈락, 같거나 거의 같은 질문 쌍, intent·문서 분포, 경고. 문서 집중도 경고는 문서가 2개 이상일 때만 낸다. 점수를 만들지 않는다. |
| `evaluators/qa_judge.py` (신규) | Stage 2. QA당 1회 호출로 groundedness, correctness, completeness, question_quality를 판정한다. 주장별 근거(`evidence`), 실패 유형, 이유를 받는다. 실패는 `error`로 남기고 점수 계산에서 뺀다. 한도 초과는 작업 전체를 멈춘다. 언어 정책 4종을 적용한다. |
| `evaluators/pipeline_v2.py` (신규) | Data Validation → Judge. 결과는 원본 인덱스와 맞춘다. 원문 언어와 QA 언어를 따로 정한다. |
| `tests/test_eval_v2.py` (신규) | 22개. v1 실패 표시 검사 3개를 포함한다. LLM은 mock이다. |
| `.github/workflows/ci.yml` | 백엔드 테스트에 `test_eval_v2`를 추가했다. |

점수 규칙 (초기값):
- QA 점수 = 근거성 0.35 + 정확성 0.30 + 완전성 0.20 + 질문 품질 0.15
- Hard Fail: 근거성 또는 정확성 < 0.6, 또는 원문과 모순되는 주장이 있을 때. 최종 점수에 0.5배로 들어간다.
- 통과: Hard Fail이 아니고, QA 점수 ≥ 0.70이고, 질문 품질 ≥ 0.5
- 평가 실패가 20%를 넘으면 등급을 매기지 않는다.

## 실측 (Gemini 2.5 Flash, 일부러 결함을 넣은 QA 10건, DB 미사용)

| 사례 | 판정 |
| --- | --- |
| 정상 (표 수치) | 통과, 4개 지표 모두 1.0 |
| 표에서 다른 열(전주) 값을 답함 | correctness 0.0 → Hard Fail, `numeric_error` |
| 원문에 없는 이유를 덧붙임 | groundedness 0.3 → Hard Fail, `unsupported_claim` |
| "위 표에서 두 번째 행" 질문 | question_quality 0.2, `ambiguous_question` |
| 원문으로 답할 수 없는 질문 | 모든 지표 0, `unanswerable_question` |
| en→ko 정상 (15%p) | 통과 |
| en→ko 15 percentage points → "15%" | correctness 0.2, `unit_mismatch` |
| en→ko may improve → "향상된다" | 모순 주장 → Hard Fail, `modality_mismatch` |
| en→ko not significant → "유의미했다" | 모순 주장 → Hard Fail, `negation_error` |
| ko→en "신규 가입자 제외" 조건 누락 | completeness 0.5, `condition_omitted` |

- 처음에는 지시어 질문이 question_quality 0.2인데도 가중치가 15%뿐이라 QA 점수 0.88로 통과했다. 그래서 질문 품질 0.5 미만이면 불통과로 처리하는 조건을 추가했다(감점 배율은 적용하지 않는다).
- 문서 판별 함수(`detect_language`)는 200자 미만을 항상 ko로 본다. 질문·답변은 짧으므로 QA 언어 판별에는 짧은 텍스트용 기준을 따로 쓴다.
- 기본 평가 모델(GPT 5.6 Luna)로는 아직 실측하지 않았다.

## 확인

- 백엔드 단위 테스트 74개 모두 통과: 기존 52개 + `test_eval_v2` 22개.

## 남은 일

- 5단계: v1/v2 비교 스크립트와 시나리오별 골든셋(ko→ko, en→en, en→ko, ko→en). 사용자가 라벨을 확인한다.
- 6~8단계: API의 `eval_version` 선택, 평가 화면 2단계 구성과 버전 분기, 가중치 보정 후 기본값 전환.
- 생성 결과에 청크의 `source_language`를 함께 저장하는 작업(지금은 판별값을 쓴다).

# 평가 v2 화면 (API 연결, 평가 화면, 리포트)

> 기획: [PLAN_261117_EVAL_V2_UI.md](../Plan/PLAN_261117_EVAL_V2_UI.md)
> 기본 평가는 계속 v1이다. QA Pipeline의 "평가 방식"에서 v2 미리보기를 고를 때만 v2로 평가한다.

## 백엔드

- `POST /api/evaluate`에 `eval_version`(`v1` 기본, `v2`) 인자를 추가했다. 다른 값을 보내면 오류를 돌려준다.
- `pipeline._run_v2`:
  - v2로 평가하고, v1과 같은 테이블·칸에 저장한다.
  - `metadata.eval_version = "v2"`, `judge_version`을 기록한다.
  - 등급을 보류하면 `final_grade = "보류"`로 저장한다.
- `pipeline_v2.build_v2_report`: QA별 행을 `pipeline_results.layers.quality.qa_scores`에 넣는다.
  - 이력 내보내기(RPC `get_eval_qa_scores` → `build_export_detail`)가 v1과 같은 경로로 v2 결과를 읽게 하기 위해서다. 그래서 RPC와 스키마는 바꾸지 않았다.
  - `qa_index`는 원본 QA 순서 기준이다.
  - 행에는 v1 화면이 읽는 키(`rag_avg`, `quality_avg`, `pass`, `failure_types`, `primary_failure`)도 채운다.
  - 같은 행을 `rag`에 또 넣지 않는다(저장 크기 때문).
- 작업 상태의 레이어는 v2에서 `validation`, `judge` 두 개다(`EvaluationManager.set_layers`).
- 테스트 3개 추가: 보고서 행·요약, 이력 내보내기의 원본 인덱스 정렬, v2 작업 완료 흐름. `test_eval_v2`는 25개가 됐다.

## 프론트

| 화면 | 변경 |
| --- | --- |
| QA Pipeline | "평가 방식 v1(기본) / v2 미리보기" 선택을 추가했다. v2를 고르면 평가 모델 설명 문구가 바뀌고, 진행 막대가 데이터 검증 → AI 품질 평가 2개가 되며, 완료 카드에 통과·등급·근거·수치 오류·평가 실패가 나온다. |
| Evaluation | 머리글에 v1/v2 배지와 결론 한 줄을 넣었다. 요약 카드는 전체 QA, 품질 통과, 등급(보류 사유 포함), 근거·수치 오류다. 데이터 통계 레이더 차트 대신 데이터 검증 카드를 둔다(구문 정상, 중복 의심과 [보기], 문서 쏠림 경고, 펼치면 질문 의도 분포). AI 품질 평가 카드는 지표 4개와 언어 조합 분포를 보여 준다. 실패 유형 칩을 누르면 표가 걸러진다. 표는 v2에서 QA 점수와 언어 칸을 쓴다. |
| QA 상세 보기 | v2에서는 지표 4개(기준 미달 강조), 판정 이유, 언어 정책과 언어 검사 칩, 주장별 근거(지지·근거 없음·모순, 원문 인용)를 보여 준다. 구문 제외와 평가 실패는 그 이유를 표시한다. |
| 이력 드롭다운 | v2 결과에 배지를 단다. |
| HTML 리포트 | v2 전용 빌더(`htmlBuilderV2.ts`)를 새로 만들었다. 결론, 요약, AI 품질 평가(기준선이 있는 막대, 실패 유형), 데이터 검증(중복 쌍 목록, 의도 분포), 불통과 QA(근거·수치 오류 먼저, 문제 주장과 원문 인용), 전체 QA(판정 필터, 행을 펼치면 근거), 평가 기준 순서다. 다크 모드, 모바일 폭, 인쇄를 지원하고 모든 데이터는 HTML 이스케이프한다. |
| xlsx | v2는 Summary, Validation, Detail, Evidence 시트를 쓴다. |

- v1 결과는 화면, HTML, xlsx 모두 기존 코드 경로를 그대로 탄다.

# 작업 ID 형식

> 기획: [PLAN_261117_JOB_ID.md](../Plan/PLAN_261117_JOB_ID.md)

- **문제:** 대시보드 최근 작업 목록은 생성 결과 기준이라 작업 ID가 모두 `gen_…`이었다. 그 생성에 연결된 평가 ID(`eval_…`)는 ID만으로는 묶을 수 없었다.
- **변경:**
  - 앞으로 만드는 작업부터 transaction 형식을 쓴다. QA 생성은 `TX-YYMMDD-XXXXXX`, 그 평가는 `{생성 ID}-E번호`다(`backend/job_ids.py`).
  - 무작위 6자리는 헷갈리는 0, 1, I, L, O를 뺀 대문자·숫자다.
  - 평가 번호는 같은 생성으로 저장된 평가와 메모리에 있는 평가 작업 중 가장 큰 번호 + 1이다.
  - 생성이 옛 형식이거나 찾을 수 없으면 평가에도 새 `TX-…`를 붙인다.
- **유지:** 기존 `gen_…`, `eval_…` 기록과 문서 수집 작업 ID(UUID)는 그대로 둔다. ID 형식에 기대는 코드는 없었다. DB 스키마는 바꾸지 않았다.
- **대시보드:** 최근 작업 ⓘ 상세에 평가 ID 한 줄을 추가했다.
- **확인:**
  - `test_job_ids` 6개 추가. CI 목록에도 넣었다. 백엔드 단위 테스트 82개 모두 통과.
  - API 모듈 import 확인, 프론트 `tsc` 통과.
  - 평가 번호를 정할 때 Supabase에서 생성·평가 ID를 찾는 부분은 실제 DB로 확인하지 않았다(운영 DB 조회 안 함). 조회가 실패하면 새 TX ID로 대체한다.

# 평가 v2 데이터 검증 카드 개선

> 사용자 피드백: v2 데이터 검증 카드가 숫자 두 개뿐이라 비어 보이고 v1보다 아쉽다. 자체 제안에 GPT 조정안을 반영했다.

## 변경

- **구성:** 상태 게이지 2개(구문 정상률, 중복 의심 없음 비율) + 질문 의도 분포 트리맵 + 상태 줄.
  - 게이지는 v1 원형 게이지와 같은 링 모양이다. 점수가 아니라 상태를 색으로 표시한다: 정상 초록, 중복 의심 주황, 구문 탈락 빨강.
- **빼고 바꾼 것:**
  - 의도 균형도 게이지는 넣지 않았다. 분포가 고르다고 품질이 높은 것은 아니다.
  - "중복 없음" 대신 "중복 의심 없음"이라고 쓴다.
- **중복 비율:** 쌍 수가 아니라 중복 의심 쌍에 걸린 QA 수로 계산한다. 백엔드 결과에 `duplicate_qa_count`를 추가했다. 이전 결과는 쌍 목록에서 계산한다.
- **트리맵:** 데스크톱에서는 항상 보이고 모바일에서는 접혀 있다. QA가 20개 미만이면 "표본이 적어 참고용" 안내를 붙인다.
- **문서별 QA 막대:** 문서가 2개 이상일 때만 보인다.
- **상태 줄:** 문제가 없으면 "구문 오류 및 중복 의심 없음" 한 줄을, 문제가 있으면 구문 탈락·중복 의심([보기])·문서 쏠림 칩을 보여 준다.
- **카드 높이:** 옆 AI 품질 평가 카드 높이에 맞춰 늘리지 않는다(그리드 `items-start`).
- **HTML 리포트:** 데이터 검증 절을 같은 정보(구문·중복 카드, 상태 줄, 의도 분포와 비율, 문서별 QA)로 맞췄다. 게이지는 넣지 않았다.

## 함께 고친 버그

- v2의 문서 분포와 문서 쏠림 경고가 `docId`로 계산되고 있었다. 그런데 `docId`는 청크 ID다(`generators/worker.py`).
  - 그래서 문서 하나에서 만든 QA에도 "문서 쏠림" 경고가 뜰 수 있었다.
  - 이제 QA에 문서명(`source_doc`)이 있을 때만 문서 분포를 센다. 지금 평가 데이터에는 이 값이 없으므로 문서 분포와 쏠림 경고는 나오지 않는다.
- 테스트 2개를 추가했다: 청크 ID를 문서로 보지 않음, 중복 QA 수와 쌍 수 구분.

## 확인

- 백엔드 단위 테스트 84개 모두 통과. 프론트 `tsc`, 프록시 테스트 2개, `next build` 모두 통과.
- 목업으로 HTML을 다시 생성해 데이터 검증 절 내용을 확인했다.
- 화면 스크린샷은 브라우저 라이브러리가 없어 찍지 못했다.

## 관찰 (후속 과제)

- 목업에서 "11월 17일 서울 매매가격 변동률은?"과 "11월 17일 부산 매매가격 변동률은?"이 문자열 유사도 0.91로 중복 의심이 됐다.
- 표 기반 QA처럼 질문 틀이 같고 대상만 다른 경우, 문자열 유사도로는 오탐이 생긴다.
- 후보: 숫자·고유명사가 다르면 제외하는 규칙, 또는 임베딩 유사도와 함께 판정.

## 데이터 검증 카드 2차 수정 (실화면 피드백)

- **증상:**
  - 질문 의도 분포 트리맵이 빈 칸으로 나왔다. 트리맵은 부모 높이의 100%를 쓰는데, 늘어나지 않는 카드에서는 정해진 높이가 없어 차트 높이가 0이 됐다.
  - 수정 전에 저장된 v2 결과의 문서별 QA에 청크 UUID가 나왔다.
  - 왼쪽 카드가 길고 오른쪽 품질 카드가 짧아 균형이 맞지 않았다.
- **변경:**
  - 의도 분포를 트리맵 대신 의도별 가로 막대(의도 색은 v1과 같음, 개수와 비율 표시)로 바꿨다.
  - 데이터 검증 카드는 게이지 2개 + 의도 분포 막대 + 상태 줄 순서다.
  - AI 품질 평가 카드와 2단으로 같은 높이에 두고, 상태 줄은 카드 아래쪽에 붙인다.
  - 문서 분포와 문서 쏠림 경고에서 UUID 형태의 키(옛 결과의 청크 ID)는 화면과 HTML 리포트 모두에서 거른다.
- **확인:** 프론트 `tsc`, `next build` 통과. 화면 스크린샷은 이 환경에서 찍지 못했다.

## 데이터 검증·AI 품질 평가 카드 3차 수정

- **차트 선택 검토:**
  - 트리맵은 부분-전체 비중을 면적으로 보여 주는 차트라 Judge 지표에는 맞지 않는다. 지표는 서로 독립인 0~1 점수이고 기준선과 비교해야 한다.
  - 의도 분포에는 쓸 수 있다. v1과 모양을 맞추기 위해 높이를 고정한 트리맵으로 되돌렸다.
- **데이터 검증 카드:** 게이지 2개, 질문 의도 분포 트리맵(160px 고정, `IntentTreemap`에 `height` 옵션 추가), 표본이 적을 때 안내, 상태 줄 순서다.
- **AI 품질 평가 카드** (`V2QualityPanel`):
  - 판정 누적 막대: 통과, 불통과, 근거·수치 오류, 평가 실패, 구문 제외.
  - 지표 막대: 지표별 기준선(0.6/0.6/0.7/0.5)과 기준 미달 건수를 표시한다. 건수는 QA 상세가 로드된 뒤에 보인다.
- **HTML 리포트:** AI 품질 평가 절에 같은 판정 누적 막대를 넣었다.
- **확인:**
  - 목업 리포트에서 판정 구성(통과 2, 불통과 1, 근거·수치 오류 3, 평가 실패 1, 구문 제외 1)의 합이 전체 8개와 맞았다.
  - `tsc`, `next build` 통과. 화면 스크린샷은 찍지 못했다.

# 문서 갱신과 함께 고친 버그 2건

## v2 등급 보류 저장 실패

- **원인:** `qa_eval_results`의 `chk_grade` 제약은 `A+`~`F`만 허용한다. 그런데 v2는 등급을 보류할 때 `final_grade = "보류"`를 저장하려 했다. 그래서 평가 실패가 20%를 넘은 v2 결과는 저장이 실패하고(오류 로그만 남음) 이력에 남지 않았다. REF_DB 문서를 고치다가 찾았다.
- **변경 (스키마는 그대로):**
  - 보류는 `final_grade = "F"`로 저장하고 `metadata.grade_withheld`에 사유를 남긴다.
  - 화면은 이 값이 있으면 "보류"로 표시한다: 이력 드롭다운, 대시보드 최근 작업. v2 평가 화면은 원래 판정 요약에서 읽는다.
  - 대시보드 등급 분포에서는 보류를 빼서 F로 세지 않는다.

## 작업 ID 충돌 확률 설명 과장

- **발견:** 1만 개 충돌 테스트가 가끔 실패했다. 30^6(≈7.3억) 공간에서 1만 개를 뽑으면 생일 문제로 약 7% 확률로 하나가 겹친다. 기획의 "겹치지 않는다"는 과장이었다.
- **실제 영향:** 하루 n건이면 충돌 확률은 약 n²/(2×7.3억)이다. 100건이면 0.0007%다.
- **변경:**
  - 같은 서버의 진행 중 작업과 겹치면 다시 뽑는다(`taken`).
  - DB `job_id` UNIQUE 제약이 마지막 방어선이다.
  - 테스트는 무작위성(200개)과 재추첨 확인으로 바꿨다.

## 문서

- REF_EVAL: 평가 v2 절을 추가했다. 구조, 점수·판정, 언어 정책, 주의점. v1 통계 항이 상수라는 점과 v1 실패 표시도 적었다.
- REF_BACKFLOW, REF_DB: 작업 ID 형식, `eval_version`, `metadata` 키, 등급 보류 저장 방식.
- REF_FRONTFLOW: v2 평가 화면, 평가 방식 선택, v2 내보내기.
- REF_PROMPTS: v2 통합 Judge 프롬프트 항목.
- README, backend README: v2 모듈과 `eval_version` API 인자.

## v2 HTML 리포트 QA 구성 (Evaluation 화면과 같게)

v2 HTML 리포트의 QA 부분을 Evaluation 화면(v2)과 같은 구성으로 바꿨다.

- **불통과 QA 절:** 화면에 없는 절이라 뺐다. 기획 3장의 "불통과 QA 먼저" 결정은 화면과 같게 맞추는 것으로 대체한다.
- **상세 평가 결과 표:**
  - 화면과 같은 `QA_PAGE_SIZE`(5)로 쪽을 나눈다.
  - 판정 필터가 있다.
  - 실패 유형 칩을 누르면 그 유형만 걸러진다(한 번 더 누르면 해제).
- **상세 보기:**
  - 행을 누르면 목록 대신 그 QA의 상세 화면이 나온다. QADetailView와 같은 구성이다.
  - 상세 화면에는 ← 목록으로 단추와 필터 결과 안에서 움직이는 이전·다음 단추가 있다.
  - 내용은 번호, 판정, QA 점수, 실패 유형, Q/A, 사유, 지표 4개, 주장별 근거, 언어 검사다.
- **인쇄:** 전체 행과 모든 QA 상세를 이어서 출력한다.
- **확인:**
  - `tsc`, lint, 목업 리포트 생성(행 8, 상세 8, 실패 유형 칩 4, PER=5), 스크립트 문법 검사를 통과했다.
  - 브라우저 동작은 Playwright 실행 라이브러리가 없어 확인하지 못했다.
