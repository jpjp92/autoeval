# LLM 청킹 동시 호출 확대 (2026-11-22)

> 상태: 구현 완료(2026-11-22). 결과는 [DEV_261117.md](../History/DEV_261117.md)의 "LLM 청킹 동시 호출" 절.

## 1. 배경

- 큰 PDF(해양경찰청, 청크 14만 자)는 청킹에만 약 2분이 걸렸다.
- DB 기록으로 보면 1천 자당 시간은 4월과 비슷하다. 코드가 느려진 게 아니라 문서가 크다.
- 청킹 시간은 대략 배치 수 × 배치당 4~10초 ÷ 동시 호출 수다. 배치당 시간은 Gemini가 답을 만드는 시간이다.
- 기존 동시 호출 수는 3(50쪽 이하) 또는 5였다.
- 호출마다 `asyncio.to_thread`를 썼다. 기본 스레드 풀이 `코어 수 + 4`라, 1코어 서버에서는 동시 호출 수를 올려도 5개에서 막힐 수 있었다.

## 2. 변경

1. **비동기 클라이언트:** `client.aio.models.generate_content`로 호출한다. 스레드를 쓰지 않는다.
2. **동시 호출 수:**
   - 기본값은 50쪽 이하 8, 51쪽 이상 10이다. DOCX는 블록 수 기준으로 같은 값을 쓴다.
   - 환경변수 `LLM_CHUNK_PARALLEL`이 있으면 모든 티어에 그 값을 쓴다.
3. **429 재시도:** 2초, 4초, 8초 기다리며 최대 3번 다시 시도한다. 모두 실패하면 지금처럼 `APIQuotaExceededError`로 중단한다.
4. 배치 크기, 프롬프트, 모델, 후처리는 그대로다. 청크 결과는 바뀌지 않는다.

## 3. 비용

- 호출 횟수와 토큰 수가 같으므로 비용은 그대로다. 429로 거절된 요청은 과금되지 않는다.
- 검증에 실제 호출 3번(약 $0.15 추정)을 썼다.

## 4. 검증

- **단위 테스트:** `backend/tests/test_chunk_parallel.py`. 기본값, 환경변수, 429 재시도 성공·포기, 다른 오류는 재시도하지 않는지 확인한다.
- **영문 번역 재시도 테스트:** 비동기 호출 함수를 흉내 내도록 고쳤다.
- **실측:** 같은 PDF로 기존 코드와 새 코드의 시간, 청크 수, 폴백 수를 비교한다.
